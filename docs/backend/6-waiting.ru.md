# 6. Прогоны, которые ждут

До сих пор каждый прогон жил столько, сколько один HTTP-разговор: запустили,
прочитали поток, готово. Седьмой пайплайн примера так не может. Он пишет
черновик ответа и останавливается, пока его не прочтёт агент поддержки — через
минуту, после обеда или завтра.

```json
{"id": "review", "type": "wait", "input": "review",
 "outputs": {"verdict": "verdict",
             "reply.$": "has(output.text) && output.text != '' ? output.text : vars.reply"},
 "timeout": "1d", "on_timeout": "escalate_unreviewed", "next": "decide"}
```

[Узел `wait`](../wait-node.ru.md) — часть ядра. Эта страница — про часть
бэкенда: где живёт прогон, пока на него никто не смотрит, как до него доходит
ответ и что с ним будет при перезапуске сервера.

## Хранилище для ждущих прогонов

Поток, заблокированный на сутки ради одного прогона, — это поток, слот и
обещание, что процесс не перезапустят. Вместо этого прогон пайплайна с `wait`
получает хранилище чекпоинтов; дойдя до ожидания, он сохраняется, и `run()`
возвращается:

```python
durable = any(node.type == "wait" for node in pipeline.nodes)
session = Session(..., store=store if durable else None)
```

```python
result = await session.run()
if result.waiting:          # {"node": "review", "input": "review", "deadline": ...}
    run.status = "waiting"  # здесь поток заканчивается
```

К хранилищу обращаются только такие пайплайны; остальные шесть работают в
памяти, как и раньше. Ждущий прогон не засчитывается в лимиты прогонов из
[главы 5](5-tenants.ru.md) — он ничего не держит.

## Ответ

Один эндпоинт:

```
POST /api/run/<id>/input   {"type": "review", "payload": {"verdict": "approve"}}
```

Он продолжает прогон из хранилища, в новом потоке:

```python
session = await Session.restore(store, run.id, policy=policy_for(run.plan))
await session.input("review", payload)
result = await session.run()     # до конца или до следующего wait
```

Три отказа, все `409`: прогон не ждёт, ждёт ввода другого типа или на него уже
ответили. Последний важнее всех — два агента, одновременно нажавшие
«Согласовать», не должны отправить ответ дважды. Внутри одного процесса это
решает блокировка; между процессами — хранилище: `run()` отказывается
продолжать прогон, который уже продолжил кто-то другой (`CheckpointConflict`),
и делает это до того, как что-либо выполнить.

Редактор следит за прогоном как раньше. Поток событий ждущего прогона
заканчивается событием `waiting`; после ответа тот же журнал продолжается, и
клиент дочитывает его с места остановки через `?from=N`.

## Что хранит хост

`restore` нужна политика, а чекпоинт её намеренно не содержит: это данные, и
данные могли бы расширить собственные права. Поэтому бэкенд хранит рядом с
каждым сохранённым прогоном, кому он принадлежит и на каком тарифе идёт, —
таблица из трёх колонок в том же файле SQLite. Владение — дело платформы, как
в [главе 5](5-tenants.ru.md); ядро хранит только сам прогон.

## После перезапуска

При старте сервер проходит по этой таблице и возвращает все прогоны, чей
чекпоинт всё ещё ждёт. Для агента ничего не произошло: у прогона тот же id и
тот же статус, и ответ его продолжает.

Системный тест примера делает ровно это по HTTP: запускает прогон, читает
поток до `waiting`, убивает сервер, поднимает новый на той же базе, отправляет
ответ, читает результат.

## Дедлайны

На ждущем прогоне никто не спит, поэтому никто не заметит, что его сутки
истекли. В примере для этого цикл в `main.py`:

```python
while True:
    await asyncio.sleep(config.DUE_CHECK_SECONDS)
    for run_id in await store.due():
        continue_without_input(run_id)      # прогон идёт в `on_timeout`
```

В развёртывании побольше это cron или планировщик, который у платформы уже
есть. Своих таймеров ядро не заводит: оно хранит дедлайн и отвечает на вопрос
«чьи истекли».

## Секреты

Фрейм ждущего прогона пишется на диск, а с ним и всё, что в нём лежит. Пример
отказывается запускать пайплайн с `wait`, если прогон понёс бы секреты — ключ
API, подставленный из окружения, или переменную, которую редактор пометил как
секретную. Платформа, которой нужно и то и другое, хранила бы ссылку на секрет
и разрешала её в стадии, а не значение во фрейме.
