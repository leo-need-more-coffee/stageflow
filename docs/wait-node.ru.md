# Узел wait

Одни пайплайны заканчиваются за секунду. Другие останавливаются на полпути и
ждут человека: руководитель согласует расход, клиент отвечает на вопрос,
ревьюер даёт добро — сегодня или в следующий четверг. Узел `wait` и есть эта
остановка.

```json
{
  "id": "ask",
  "type": "wait",
  "input": "approval",
  "outputs": { "decision": "decision", "comment": "comment" },
  "timeout": "7d",
  "on_timeout": "remind",
  "next": "decided"
}
```

- `input` — тип ввода, которого ждём; приходит через `session.input(type, payload)`.
- `outputs` — поля полезной нагрузки в переменные, ровно как у
  [стадии](stage-node.ru.md), включая выражения `.$`.
- `timeout` — секунды или `"90s"`, `"15m"`, `"2h"`, `"7d"`. Необязателен; с ним
  `on_timeout` указывает, куда идти, если ничего не пришло. Одно без другого —
  ошибка валидации.
- `next` — куда идти с ответом.

## Два способа ждать

Граф один и тот же; как ждать, решает хост — даёт сессии хранилище или нет.

**В памяти.** Без хранилища сессия ждёт как любая корутина: `run()` вернётся,
когда придёт ввод или истечёт таймаут. Годится для минут — чат, отладка, тест.
Ожидание — время простоя: оно не идёт в лимит `seconds` и в таймаут стадии.

```python
session = Session(id="r1", pipeline=pipeline)
task = asyncio.create_task(session.run())
...
await session.input("approval", {"decision": "approve"})   # из HTTP-обработчика
result = await task
```

**С сохранением.** С хранилищем прогон, дошедший до `wait` без ввода,
сохраняется, и `run()` сразу возвращается:

```python
from stageflow import Session, SQLiteStore

store = SQLiteStore("runs.db")
result = await Session(id="r1", pipeline=pipeline, policy=policy, store=store).run()
result.waiting   # {"status": "waiting", "node": "ask", "input": "approval", "deadline": 1767...}
```

Процесс свободен; прогон — это строка в хранилище. Когда придёт ответ — через
час, в другом процессе, после деплоя — хост восстанавливает прогон и отдаёт ему
ввод:

```python
session = await Session.restore(store, "r1", policy=policy)
await session.input("approval", {"decision": "approve"})
result = await session.run()   # дальше от `ask` до конца или до следующего wait
```

Пайплайн без узлов `wait` обращается к хранилищу только чтобы отметить начало
и конец прогона, так что мгновенные пайплайны за это ничего не платят.

Пример-бэкенд делает всё это по HTTP — эндпоинт ответа, возврат прогонов после
перезапуска, проверку дедлайнов — см.
[Свой бэкенд, 6. Прогоны, которые ждут](backend/6-waiting.ru.md).

## Что сохраняется

Фрейм, узел, на котором прогон остановился, потраченные метры, полученный
ввод, дедлайны ожиданий — и **сам пайплайн**. Прогон продолжается с тем
графом, с которым начался: правка пайплайна меняет новые прогоны, а не уже
ждущие.

**Политика** не сохраняется. Чекпоинт — это данные, их можно отредактировать,
поэтому хост передаёт политику в `restore` заново, ровно как в
[`from_snapshot`](session-control.ru.md). Прогон, восстановленный под более
узкой политикой, чем начинался, отвергается при валидации.

## Таймауты

Дедлайн — абсолютное время, оно фиксируется, когда прогон впервые доходит до
`wait`, и хранится вместе с прогоном. На нём никто не спит, поэтому кто-то
должен проверять: хост спрашивает у хранилища, у каких прогонов дедлайн
прошёл, и восстанавливает каждый без ввода — прогон видит, что время вышло,
и идёт в `on_timeout`.

```python
for run_id in await store.due():
    session = await Session.restore(store, run_id, policy=policy_of(run_id))
    await session.run()
```

Раз в минуту из cron, из планировщика, который в приложении уже есть, или
циклом в бэкенде. Своего планировщика StageFlow не несёт: где и как часто
смотреть — решение хоста, как и то, где живёт хранилище.

## Два процесса, один прогон

Каждое сохранение указывает, какую версию прогона оно заменяет. `run()` у
восстановленной сессии сначала помечает прогон как выполняющийся; если другой
процесс успел раньше, он поднимает `CheckpointConflict` **до того, как
что-либо выполнить**. Двойной клик по «Согласовать» продолжит прогон один раз.

Прогон, чей процесс умер посреди работы, остаётся помеченным как
выполняющийся. Чтобы его восстановить, нужен `takeover=True` — это хост
говорит «того процесса больше нет»: отличить мёртвый процесс от медленного
StageFlow не может.

## Падения между ожиданиями

С `checkpoint="every_node"` прогон сохраняется ещё и после каждого узла
основного графа, так что при падении теряется не больше узла, который
выполнялся. Этот узел выполнится снова после `restore(takeover=True)` — хотя бы
раз, а не ровно один. Стадия с побочными эффектами должна передавать свой
`idempotency_key` тому, кого вызывает (платёжному провайдеру, почтовому
сервису): ключ одинаков у упавшего прогона и у того, что его повторил.

```python
class Charge(BaseStage):
    async def run(self):
        await payments.charge(amount, idempotency_key=self.idempotency_key)
```

Сохранение после каждого узла стоит записи на узел, поэтому оно для длинных
пайплайнов из медленных стадий, а не для цепочки быстрых.

## Где может стоять wait

Сохранённый прогон возвращается в один узел основного графа. Поэтому `wait`
не может стоять внутри блока `try`, тела `map`, ветки `parallel` или в
субпайплайне: валидация это отвергнет и назовёт блок. Ждите до блока или после
него — `wait` сразу за `parallel` получит всё, что сделали его ветки.

## Хранилища

| | |
|---|---|
| `MemoryStore()` | словарь: тесты и один процесс, которому ожидания должны освобождать руки |
| `SQLiteStore(path)` | файл; несколько процессов на одной машине; только стандартная библиотека |

Всё остальное — Postgres, Redis — это класс с четырьмя корутинами: `load`,
`save(checkpoint, expected)`, `due(now)` и `delete`. `save` должен отказывать,
если сохранённая версия не `expected`; именно эта проверка не даёт двум
процессам продолжить один прогон.

## События

| Событие | Когда |
|---|---|
| `waiting_started` | прогон дошёл до wait; в payload `input`, `deadline` |
| `wait_completed` | ввод пришёл |
| `wait_timed_out` | дедлайн наступил раньше |
| `session_suspended` | прогон сохранён вместо ожидания |
| `session_restored` | прогон загружен из хранилища |

Каждый раз, когда восстановленный прогон снова входит в свой `wait`, узел ещё
раз считается шагом.
