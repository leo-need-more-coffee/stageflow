## 1. Модель скоупинга: local + global

Вместо одного плоского Context — два явных namespace:

- **`local`** — данные текут вдоль пройденного пути исполнения, а не по всему графу. `condition`/`parallel` не имеют своих `outputs` и прозрачно транслируют входящий `local`-фрейм дальше (в `then`/`else`, во все `children`) — поэтому значению не нужно явно прокидываться через каждый промежуточный узел вручную. Единственная настоящая граница скоупа — `subpipeline`: свежий child-`Context`, пересечение только через явные `inputs`/`artifact_outputs`/`result_output` (эта часть уже есть в коде сегодня, менять не нужно).
- **`global`** — session-wide, доступен отовсюду, но запись только по явному указанию. На практике нужен в основном на входе (посев из внешнего payload) и на выходе (то, что должно пережить весь локальный путь, например итоговый summary). В отличие от `local`, у `global` нет ветковых границ — это по-настоящему плоский неймспейс на всю сессию.

  > **Пересмотрено в 0.7.0: посев переменных — узел `entry`.** Роль «посев на входе», которую в этом разделе носил `global`, а после 0.6.0 закрывал входной фрейм сессии, стала первоклассной частью пайплайна: узел типа `entry` объявляет переменные, с которыми граф стартует, и сам является его началом (поле `entry` в шапке JSON выводится из него). Значения — по умолчанию: пришедшее снаружи их перекрывает, поэтому один пайплайн запускается и сам по себе, и параметризованно. Разбор — `REFACTORING.md` §11.

  > **Пересмотрено в 0.6.0: `global` удалён.** Обе заявленные роли на практике закрывал `local`: посев — это входной фрейм сессии, а «пережить путь» — свойство фрейма, который и так течёт до терминала. Хуже того, ни одна из них не работала сквозь: терминал собирает артефакты только из фрейма, а `subpipeline` стартует со свежим контекстом и своим `global`, так что провести значение от записи до выхода было нельзя без `expose` обратно в `local`. Единственное, что `global` умел реально, — разделяемое мутабельное состояние поперёк ветвей `parallel` с семантикой «кто последний, тот и прав», то есть отказ от той самой гарантии, которую `parallel` даёт для фрейма (конфликт записи двух ветвей — явная ошибка). Аккумулятор поперёк ветвей выражается строже: каждая ветка пишет своё имя, узел после `parallel` их складывает. Полный разбор — `REFACTORING.md` §10.
- **`consume`** — отдельное поле узла (список имён аргументов), а не часть каждого `arguments`-маппинга: помечает, что после этого шага значение нужно физически убрать из фрейма (типовой случай — секрет вроде `creds`, который не должен быть читаем 20 узлов спустя, хотя механически мог бы).

### 1.1 Прецеденты

Модель проверена не только умозрительно. У AWS Step Functions раньше была ровно противоположная модель — явный проброс данных через каждый intermediate state (`InputPath`/`OutputPath`, JSONPath). В конце 2024 они сами добавили персистентные **Variables** (`Assign`) именно потому, что старая модель заставляла "passing data through multiple intermediate states" — лишние переходы, лишняя сложность, лишние деньги за transitions. Скоупинг их Variables — один в один наша модель: outer-скоуп виден изнутри (вниз), но переменная, присвоенная внутри одной ветки `Parallel` или одной итерации `Map`, не видна ни соседям, ни родителю; вложенный workflow (~ наш `subpipeline`) outer-скоуп вообще не видит.

n8n устроен так же: любая предыдущая нода адресуется по имени (`$('auth').item.json.token`) откуда угодно ниже по графу, без ручного прокидывания через промежуточные ноды.

Обратный пример — Airflow XCom: там только explicit push/pull (`xcom_push`/`xcom_pull` по `task_id`+`key`), никакого персистентного скоупа — общеизвестная боль именно из-за этого.

Вывод: `local` ≈ AWS "outer/inner scope" + n8n cross-node reference. Про `global` вывод был «то, чего у AWS нет вообще» — и именно это в 0.6.0 пришлось переоценить: у AWS переменные ветки не переживают `Parallel` **вообще**, и это осознанное решение, а не пробел. Отсутствие аналога у трёх из трёх рассмотренных систем — аргумент против второго уровня, а не за него.

## 2. Синтаксис в JSON

Bucket-структура вместо плоских путей: `arguments`/`outputs` делятся на именованные секции, значения внутри — просто имена, без префикса `local.` (бакет уже определён секцией).

```json
{
  "id": "auth",
  "type": "stage",
  "stage": "AuthStage",
  "arguments": {
    "local": { "creds": "creds" },
    "const": { "timeout_s": 30 }
  },
  "outputs": {
    "local": { "token": "next" }
  },
  "consume": ["creds"],
  "next": "fetch_data"
},
{
  "id": "fetch_data",
  "type": "stage",
  "stage": "FetchDataStage",
  "arguments": {
    "local": ["token"],
    "const": { "n_max": 10 }
  },
  "outputs": {
    "local": { "data": "next" }
  },
  "consume": ["token"],
  "next": "output"
}
```

- **`arguments`** — бакеты `local` и `const` (в 0.6.0 бакет `global` убран вместе со скоупом, см. §1; в 0.7.0 бакет `local` переименован в `vars` — см. врезку ниже).
  - `local` — ссылки на фрейм: `{"имя_аргумента": "имя_поля_во_фрейме"}`; списочный сахар `["creds"]` ≡ `{"creds": "creds"}` (без переименования — типовой случай).
  - `const` — литералы как есть (числа/bool/строки), без экранирования. Нужен именно потому, что внутри `local` bare-значение теперь однозначно ссылка, а не литерал — литералам нужен свой дом. С 0.5.0 это ещё и единственный канал литеральной настройки узла: отдельного поля `config` у `stage` больше нет (`REFACTORING.md` §9).
- **`outputs`** — бакет `local` (в 0.6.0 бакет `global` убран).

  > **Пересмотрено в 0.7.0: уровень бакета в `outputs` убран, `arguments.local` → `arguments.vars`.** После удаления `global` бакет-уровень в `outputs` остался единственным возможным, то есть перестал быть выбором: `{"local": {"token": "next"}}` — это ровно `{"token": "next"}` с лишней обёрткой, которую нельзя ни поменять, ни опустить. В `arguments` выбор реальный (ссылка против литерала), поэтому бакет остался, но имя `local` описывало скоуп, которого нет, и переименовано в `vars`. То же со `variables`: секция объявления типов потеряла уровень скоупа. Полный разбор — `REFACTORING.md` §12.
  - bare-значение = «моё же поле результата стейджа с этим именем»: `{"token": "next"}` — взять `output.token`, положить в `local.next`.
  - `.$`-суффикс на ключе внутри бакета = вычислить как CEL (см. §2.1); в CEL-контексте доступны `local.*` (фрейм до этой ноды) и `output.*` (сырой результат стейджа).
- **`consume`** — как и раньше: плоский top-level список имён, действует только на `local`, удаляет их из фрейма после применения `outputs`.
- **`expose`** — новое плоское top-level необязательное поле, доступно на любом типе узла (не только `stage` — на `condition`/`parallel` тоже, они и так прозрачно транслируют `local` дальше). Чистое переименование/копирование во фрейме без запуска стейджа: ключ — имя-источник, значение — имя-назначение (с 0.6.0 межскоуповой копии больше нет — поле осталось ради переименования без хода графа; в 0.7.0 вместе с этим ушёл и префикс `local.`, которого схема требовала с обеих сторон: `{"sink": "sink_for_report"}`). По умолчанию — копия, старое имя остаётся; для «переименовать и убить старое» — добавить `consume` с исходным именем на той же ноде. Разбирали отдельно (не нода, а именно поле) — чтобы не плодить лишний тип узла и не тратить ход графа впустую.

```json
{
  "id": "route",
  "type": "condition",
  "condition": "vars.status == 'ok'",
  "expose": { "sink": "sink_for_report" },
  "then": "publish",
  "else": "retry"
}
```

Порядок обработки фрейма на ноде: `arguments` (чтение) → стейдж → `outputs` (запись) → `consume` (удаление) → `expose` (копия/переименование) → фрейм передаётся дальше по `next`.

Внутри `outputs` записи одной ноды применяются как одновременное присваивание: все значения (включая `.$`-выражения) считаются против фрейма на входе в ноду и только потом пишутся. Поэтому порядок ключей в объекте `outputs` на результат не влияет — до 0.6.0 влиял, см. `REFACTORING.md` §10.3.

Control flow (`next` у `condition`/`switch`/`parallel`/`subpipeline`/`terminal`) — всегда явная структура полей, без динамического роутинга через выражение: граф должен оставаться статически проверяемым и рисуемым для UI-редактора.

### 2.1 Что на самом деле значит `.$`

С момента, как язык выражений — CEL, а не кастомный мини-парсер путей, `.$` перестал быть про "путь или литерал" и про "простой путь или сложное выражение" — обычный `local.creds` и так валидный CEL (тривиальный field access), эти две вещи схлопнулись в одну. `.$` теперь значит буквально одно: **выполнить значение как CEL, а не взять как есть**. Ключ без `.$` — данные, ключ с `.$` — код.

С bucket-синтаксисом (см. §2) различение "литерал vs ссылка" происходит на уровне бакета (`const` vs `local`), а не суффиксом на ключе — суффикс `.$` внутри `local`-бакета по-прежнему значит ровно одно: вычислить как CEL, а не скопировать 1:1.

Рассматривался и отклонён альтернативный синтаксис — сигил `$`/`${...}` в значении (bash/Terraform/GitHub Actions-стиль: `"creds": "${local.creds}"`). Он умеет то, чего `.$` на ключе принципиально не может — интерполяцию внутри произвольного текста (`"note": "выдан для ${local.creds}"`). Цена — экранирование буквального `$` в литералах и правило сохранения типа (весь value = один `${...}` → сохраняем реальный тип; `${...}` внутри текста → всегда строка). Так как шаблонизированные строки пайплайну не нужны (значения типизированные, между стейджами не собираются логи/урлы из кусков текста), решили не платить за интерполяцию — остаёмся на `.$` на ключе: ноль экранирования, ноль правил про тип, значение всегда либо целиком код, либо целиком данные.

Отдельный нюанс для `outputs`: bare-значение там уже значит не литерал, а "моё же поле с таким именем из результата стейджа" (`"token": "token"`) — то есть у `outputs`, в отличие от `arguments`, есть implicit-неймспейс результата самой ноды. Если `outputs`-значение помечено `.$` (например, чтобы записать что-то вычисленное), CEL должен видеть не только `local.*` (фрейм таким, каким он был до этой ноды), но и `output.*` — сырой результат, который стадия только что вернула:

```json
"outputs": {
  "token": "next",
  "summary.$": "{'sent': output.count, 'total': vars.total}"
}
```

## 3. Expression-язык: заменить `core/jsonlogic.py` на CEL

Один язык выражений для `condition`/`switch` **и** для вычисляемых `arguments`/`outputs` — не два разных мини-языка в разных углах кода. Заменяет кастомный `JsonLogic` (см. `ARCHITECTURE.md` §7.7) целиком.

Проверено на практике (не только по документации) — оба существующих питоновских байндинга CEL корректно обрабатывают наш реальный набор кейсов (условие, вложенный `local.`/`global.` путь, математика, тернарник, конкатенация строк через `+`/`string()`) и корректно **падают** на опечатке в скоупе, опечатке в имени поля и на попытке выйти в питон (`__import__(...)`, `local.__class__`).

- **`common-expression-language`** (PyPI, `import cel`) — нативные байндинги, ~0.003 мс/вызов на предкомпилированной программе (`cel.compile(expr).execute(ctx)`), очень широкое покрытие платформ (linux x86_64/arm64/armv7/ppc64le/s390x, macOS x86_64/arm64, Windows, PyPy, wheels уже под cp314/cp315) — **рекомендация по умолчанию**.
- **`cel-python`** (PyPI, `import celpy`) — чистый Python, ~0.156 мс/вызов (в ~50 раз медленнее) — держать в уме как fallback, если когда-нибудь компилируемая зависимость станет проблемой (экзотическая платформа/embedded).
- Оба API идентичны по форме (`compile`/`evaluate`-подобный вызов с dict-контекстом), миграция между ними дешёвая.

## 4. Switch-нода (опционально, на будущее, не обязательна для MVP)

Для n-way ветвления — отдельный явный тип узла (не `ConditionNode`, но по той же идее), по образцу `Choice`-state в AWS Step Functions: список условий, каждое ведёт в свой `next`, плюс `default`. В UI — один видимый порт на каждый `case` (можно подписать `when`-выражением) плюс порт `default`.

```json
{
  "id": "route",
  "type": "switch",
  "cases": [
    { "when": "local.status == 'ok'", "next": "publish" },
    { "when": "local.status == 'retry'", "next": "check" }
  ],
  "default": "reject"
}
```

`when` — CEL-выражение (тот же язык, что и везде). `validate()` проверяет, что все `next`/`default` существуют в графе — статический анализ и отрисовка графа не ломаются.

`ConditionNode` (бинарный `then`/`else`) остаётся отдельным типом узла как есть — просто условие внутри CEL вместо jsonlogic. Не заменяется на generic-роутинг: явный тип узла с явными портами лучше ложится на визуальный редактор.

## 5. Parallel: слияние веток

Ветки `parallel` выполняются с независимо разошедшимися `local`-фреймами (иначе и нельзя — иначе гонка на общий мутабельный объект). Никакого нового поля в схеме `parallel` для этого не требуется — ветки состоят из обычных нод, и `outputs`/`expose` на них работают точно так же, как везде (см. §2). Не нужно ничего "прокидывать через каждую ноду вручную" (анти-паттерн, который мы уже разбирали для `local` — сюда он тоже не должен просочиться).

Прецедент проверен: у AWS Step Functions `Parallel`-стейт возвращает результаты веток строго через отдельный явный механизм — позиционный массив выходов веток (`[branch1_output, branch2_output, ...]`), а не через утечку внутренних `Assign`-переменных наружу (они изолированы внутри ветки и не переживают завершение `Parallel` вообще, даже в объемлющий скоуп).

Правило мёржа (поведение движка на `parallel`, не новый JSON-синтаксис): для каждой ветки берём diff её финального фрейма против бейзлайна (фрейм на входе в `parallel`) — наружу идут только НОВЫЕ имена, которых до входа в `parallel` во фрейме не было. Всё, что ветка меняла из уже существовавших до входа имён — branch-local scratch, наружу не просачивается (как у AWS). Коллизия имени в diff между двумя ветками — ошибка: на `validate()`, если имена статически известны, иначе в рантайме при мёрже.

Отброшенное при этом не замалчивается: имена, которые ветка переписала «в никуда», перечислены в событии `parallel_completed` (`{"merged": [...], "dropped": ["branch.name", ...]}`). Само поведение намеренное, но по фрейму оно никак не видно — ветка пишет `n = 101`, наружу выходит `n = 1`, — а раз конфликт двух веток движок сообщает явно, то и это должно быть видно в телеметрии.

```json
{
  "id": "fan_out",
  "type": "parallel",
  "branches": [
    { "id": "hash", "entry": "compute_hash" },
    { "id": "thumb", "entry": "compute_thumb" }
  ],
  "next": "merge"
}
```

## 6. Retry + try/except: обработка ошибок

Не как в Go (ручной `if err != nil` на каждом уровне) — а как исключения в обычных языках: ошибка сама бежит вверх, пока не встретит обработчик, промежуточные ноды ничего не обязаны знать и делать.

**Пересмотрено (v0.4.0).** Изначально обработка вешалась плоскими полями `retry`/`catch` на каждую ноду — по образцу AWS Step Functions. На практике это вылилось в тот самый Go-way: обработчик приходилось дублировать на каждой ноде, которая может упасть, а «одна ошибка — один обработчик на весь участок» не выражалось вовсе. Поэтому обработка ошибок стала **блочной**, как `try/except` в Python, и разделилась с повторами:

- **`retry`** остаётся полем ноды — это свойство конкретной операции («этот HTTP-вызов стоит повторить трижды»), а не участка графа. Поля: `error_equals` (имена питоновских исключений, `"*"` — поймать всё), `max_attempts`, `interval_seconds`, `backoff_rate`, опционально `max_delay_seconds`. `max_attempts` — все запуски ноды вместе с первым (три попытки = один запуск и два повтора), и счётчик у каждой политики в списке свой.
- **`try`** — отдельный тип узла, накрывающий ОБЛАСТЬ графа. Любой узел внутри области, упавший с подходящей ошибкой, уводит исполнение в свой `except`.

```json
{
  "id": "safe_fetch",
  "type": "try",
  "body": "fetch_data",
  "except": [
    { "error_equals": ["TimeoutError"], "next": "handle_timeout", "result_local": "error" },
    { "error_equals": ["*"], "next": "handle_any" }
  ],
  "next": "output"
}
```

- **Область блока** — узлы, достижимые из `body` по рёбрам управления, но НЕ достижимые из `next` (точки выхода). Состав выводится из графа, а не перечисляется руками, поэтому не может разойтись со структурой; тот же принцип, что у веток `parallel` (§5), и на нём же строится визуальный регион в редакторе.
- **`except`** — список обработчиков: `error_equals` + `next` (куда прыгнуть) + `result_local` (куда в `local` положить объект ошибки — нода-обработчик читает его как обычный `local.error.message`/`local.error.type`).
- **Порядок**: сначала исчерпываются повторы упавшей ноды, и только потом ошибка всплывает к ближайшему объемлющему `try`. Не подошедшая по типу ошибка идёт дальше наружу — ровно как в Python.
- **Вложенность** бесплатна: внутренний `try` — обычная нода внутри области внешнего.
- **Фрейм при ошибке**: обработчик видит `local` таким, каким его оставил последний успешно отработавший узел тела — как `except` в Python видит всё, присвоенное до падения.
- **Решено (было открытым):** `error_equals` матчится И по короткому имени класса (`TimeoutError`), И по полному пути (`mymod.MyError`) — что написано в JSON, то и сработает.

## 7. Диспетчинг по `type`: реестр + полиморфизм

Закрывает пункт из `ARCHITECTURE.md` (строки 155–156): сейчас диспетчинг типа узла размазан по нескольким местам (`Node.from_dict`, `Session._get_handler` — isinstance-цепочка на `_handle_stage/_handle_condition/_handle_parallel/_handle_subpipeline/_handle_terminal`, `Pipeline.validate`), добавление нового типа узла требует править всё сразу и легко забыть одно из мест.

Решение — два разных механизма, не один общий dict:

- **Парсинг** (`Node.from_dict`) — тут dict-реестр `{type_str: NodeClass}` неизбежен: есть только строка `"type": "..."`, объекта ещё нет, isinstance неприменим. Регистрация — декоратором прямо на классе (`@register_node("stage")`), чтобы не редактировать отдельный файл-реестр руками.
- **Валидация и исполнение** (`Pipeline.validate`, `Session._get_handler`) — не dict с хендлерами, а обычный полиморфизм: `execute(self, session)`/`validate(self, graph)` как методы на подклассах `Node`. Диспетчинг превращается в `node.execute(session)` — Python сам резолвит метод, никакой таблицы снаружи не нужно.

```python
# core/nodes/base.py
NODE_TYPES: dict[str, type["Node"]] = {}

def register_node(type_str: str):
    def deco(cls):
        NODE_TYPES[type_str] = cls
        return cls
    return deco

class Node:
    id: str
    next: str | None = None

    @classmethod
    def from_dict(cls, data: dict) -> "Node":
        return NODE_TYPES[data["type"]]._parse(data)

    async def execute(self, session: "Session") -> str | None:
        raise NotImplementedError

    def validate(self, graph: "Pipeline") -> list[str]:
        raise NotImplementedError
```

```python
# core/nodes/stage.py
@register_node("stage")
class StageNode(Node):
    stage: str
    arguments: dict
    outputs: dict
    consume: list[str] = []

    async def execute(self, session):
        result = await session.run_stage(self.stage, self.arguments)
        session.apply_outputs(self.outputs, result)
        session.apply_consume(self.consume)
        return self.next

    def validate(self, graph):
        return [f"{self.id}: unknown stage {self.stage}"] if self.stage not in graph.known_stages else []
```

```python
# core/session.py — было isinstance-цепочка, стало
async def _run_node(self, node: Node):
    next_id = await node.execute(self)

# core/pipeline.py
def validate(self):
    errors = [e for node in self.nodes for e in node.validate(self)]
```

Добавление нового типа узла (например, `MapNode`) — один новый файл с `@register_node("map")` и своими `execute`/`validate`; `session.py`/`pipeline.py` не трогаются вообще.
